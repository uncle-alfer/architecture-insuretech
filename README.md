## Задание 3. Переход на Event-Driven архитектуру

См. файлы в папке Task3:

- [`C4.svg`](<Task3/InsureTech_C4_сontainer-diagram.drawio.svg>)

### Что перевели на Event-Streaming

* **Публикация каталога продуктов/тарифов**:
  `ins-product-aggregator -> Kafka` (`ins.products.*`) - агрегатор в фоне собирает/нормализует данные страховых и публикует снапшоты/дельты.
* **Локальные реплики каталога**:
  `core-app ← Kafka (products.*)` и `ins-comp-settlement ← Kafka (products.*)` - оба сервиса подписываются и поддерживают свои read-модели без периодических REST-пуллов.
* **Доменные события по полисам**:
  `core-app -> Kafka (policies.*)` - при оформлении/изменении/отмене полиса;
  `ins-comp-settlement ← Kafka (policies.*)` - потребляет события вместо ночного REST.

### Будем ли использовать Transactional Outbox

**Да.**

* В **`ins-product-aggregator`** и **`core-app`** применяем `Transactional Outbox`: запись бизнес-состояния и запись «события» фиксируются одной транзакцией в БД (таблица `outbox`), отдельный relay публикует в Kafka с ретраями и идемпотентностью.
* Консьюмеры выполняют идемпотентные `upsert`-ы / дедупликацию по ключу события.
* В **`ins-comp-settlement`** outbox не обязателен (он потребитель), если только сервис сам не будет издавать новые доменные события.

### Что осталось REST и почему пунктир

* **`core-app ↔ ins-product-aggregator` - REST fallback (пунктир)**:
  используется только при необходимости (например, оперативная проверка/принудительное обновление из кеша агрегатора, когда стрим ещё не догнал).
* **`ins-comp-settlement -> core-app` - REST reconciliation (пунктир)**:
  разовые сверки/перезапуски отчётности в исключительных случаях. Основной поток - события `products.*` и `policies.*`.

## Задание 4. Проектирование продажи ОСАГО

См. файлы в папке Task4:

- [`Схема (drawio)`](<Task4/Task4.xml>)
- [`Схема (png)`](<Task4/Task4.drawio.png>)
- [`Схема (svg)`](<Task4/Task4.drawio.svg>)
- [`osago-aggregator (внутренний REST для core-app)`](<Task4/osago-aggregator.yaml>)
- [`core-app -> браузер (SSE)`](<Task4/core-app.txt>)

**Что сделали:** 

* добавили сервис **osago-aggregator** для оформления ОСАГО онлайн. Он принимает заявку, параллельно запрашивает предложения у всех страховых и публикует отдельные события по мере поступления ответов. **core-app** слушает события и стримит их в браузер по **SSE**, чтобы пользователь видел предложения сразу.

* Внешняя интеграция со страховыми - ожидание ответа **до 60 секунд** на партнёра (частичные результаты приходят раньше).
* Выдача в браузер - по **SSE** с инкрементальными событиями; резерв - периодический **REST GET**.

**Хранилище osago-aggregator:** нужно для идемпотентности, трекинга статусов, дедупликации событий и реализации **Transactional Outbox**.

**API:**

* `core-app -> osago-aggregator` - REST `POST /v1/osago/quote-requests` (старт) + `GET /…/results` (снимок/резерв).
* `osago-aggregator -> Kafka (osago.*)` - события по партнёрам и итогам.
* `core-app -> InsureTech Web` - **SSE** стрим с инкрементальной выдачей.

**Паттерны отказоустойчивости:**

* На внешних REST-интеграциях (к страховым): **Rate Limiting**, **Circuit Breaker**, **Retry**, **Timeout**.
* На init-вызовах core-app -> osago-aggregator: **Timeout/Retry/CB**.
* Внутри сервисов - **Transactional Outbox**, идемпотентные консюмеры.

**Масштабирование:** сервисы работают в нескольких экземплярах; агрегатор горизонтально масштабируется, состояние - в БД, события - через Kafka, порядок по `request_id`. Решение не зависит от единичного инстанса.
