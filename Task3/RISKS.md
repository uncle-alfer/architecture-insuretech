# Проблемы и риски, которые связаны с планируемым ростом нагрузки

## Контекст (как сейчас)

* `core-app` и `ins-comp-settlement` держат **локальные реплики** продуктов/тарифов, периодически **пулля** их из `ins-product-aggregator` (15 минут и 1 раз/сутки).
* `ins-product-aggregator` при **синхронном** запросе от сервисов **фан-аутит** вызовы ко всем страховым, агрегирует ответ **в рамках того же запроса**.
* `ins-comp-settlement` ночью дополнительно **тянет** из `core-app` список оформленных за день полисов (REST).
* Межсервисная интеграция - в основном **REST**. 

### Проблемы и риски при росте (5 -> 10 страховщиков)

1. **Линейный рост латентности и вероятность таймаутов**
   Синхронный fan-out внутри `ins-product-aggregator` масштабирует **p99 ответа** пропорционально самому медленному партнёру, а также числу партнёров. При 10 интеграциях накапливаются: долгие хвосты, Head-of-Line blocking, каскадные ретраи, рост 5xx.
2. **Каскадные сбои и деградации**
   Неустойчивость одного внешнего API (ошибки/тормоза) начинает «тянуть вниз» агрегатор и всех его потребителей. REST-цепочка увеличивает blast radius.
3. **Thundering herd/набеги**
   Периодические pull-синхронизации (`core-app` каждые 15 мин., `ins-comp-settlement` раз/сутки) создают пики нагрузки на агрегатор и внешние API в одном и том же окне.
4. **Слабая управляемость SLA и backpressure**
   REST-шторм плохо контролируется: трудно дозировать RPS по каждому страховщику, соблюдать rate-limit соглашения и изолировать пулы потоков/соединений per-partner (Bulkhead).
5. **Старение локальных реплик и неустойчивые окна консистентности**
   Между pull-циклами данные устаревают. При ошибках ночной синхронизации `ins-comp-settlement` получает неполный реестр.
6. **Single point в интеграциях**
   `ins-product-aggregator` - критичное звено. При росте количества страховщиков увеличиваются требования к его масштабированию, идемпотентности, ретраям, а также сложности с релизами.
7. **Усложнение при расширении партнёрского пула**
   Новые 5 компаний удваивают количество контрактов/форматов, ветвление логики трансформации/нормализации, объём кода ретраев и таймаутов.
8. **Ночной REST в `ins-comp-settlement` ← `core-app`**
   Длинная синхронная операция с риском таймаута/частичной выборки. Повторные прогоны ночью -> дубли, нет гарантии exactly-once без явной идемпотентности.
9. **Ограничения дальнейшего масштабирования**
   При рекламной кампании возможны резкие всплески запросов - REST-цепочки сложнее выдерживать, чем асинхронный пайплайн с буферизацией.

### Цели изменения

* Убрать синхронный fan-out из горячего пути клиентов/операций.
* Снизить задержки ответов `core-app` (читать из локальной read-реплики).
* Обеспечить устойчивость к медленным/падающим внешним API и к «набегам».
* Упростить масштабирование при добавлении 5 новых компаний.
* Перевести ночную интеграцию `ins-comp-settlement` с `core-app` на событийную модель.
